# Sauvegarde et restauration

Deux archives coexistent. Le zip fichier (`sololmnp-*.zip`) copie la base SQLite. Sur Postgres, cette route répond `BACKUP_SQLITE_ONLY`. L’archive de dossier (`dossier-*.zip`) emporte les lignes et les justificatifs enregistrés, sur SQLite comme sur Postgres. C’est celle que l’écran Conservation crée et restaure.

`POST /api/filing/backup` écrit une archive locale : copie SQLite via l’API backup, justificatifs enregistrés dans cette base (un fichier du dossier qui n’est pas en base, ou dont le nom commence par un point, comme `.gitkeep`, n’est pas archivé), manifeste (date, version, révision de schéma, millésimes fiscaux et empreinte de leurs règles, tailles, SHA-256). Aucun secret d’environnement. Le zip est composé dans un fichier temporaire puis renommé. Deux sauvegardes successives ne s’écrasent pas.

`GET /api/filing/backups` liste ces archives : date, taille, version de l’application, révision de schéma, empreinte SHA-256 et résultat du dernier contrôle d’intégrité (`unchecked`, `ok` ou `failed`). Un contrôle dont l’empreinte ne correspond plus au fichier redevient `unchecked`.

`POST /api/filing/backups/verify` rejoue les contrôles (chemins, doublons, taille, empreintes du manifeste, chemins de justificatifs, `PRAGMA integrity_check`, révision de schéma) et enregistre le résultat à côté des archives, dans `integrity.json`. Ce fichier n’entre pas dans l’archive. Le contrôle refuse une archive que la restauration refuserait.

`GET /api/filing/backups/preview?filename=` compare la base en service et l’archive : date de la sauvegarde, nombre d’écritures, nombre d’exercices. Rien n’est écrit.

`POST /api/filing/backup/restore` exige `confirmation: "RESTAURER"` et un fichier déjà présent dans la liste. Il refuse un nom contenant `..`, un lien, un doublon, une archive trop grande, une empreinte fausse, un schéma différent ou un chemin de justificatif qui n’est pas un seul nom de fichier sûr. Un nom de justificatif qui commence par un point (`.gitkeep` dans une archive déjà produite) est ignoré : il ne fait pas échouer la restauration. Avant le remplacement, une sauvegarde de l’état actuel est créée. La base extraite est contrôlée, les connexions sont fermées, le fichier SQLite est remplacé, puis les justificatifs du répertoire sont alignés sur l’archive. Les écritures validées ne sont pas modifiées une à une : la base entière est reprise telle qu’elle était. Si le remplacement échoue, la base et les justificatifs d’avant sont remis en place. Un échec de ce retour arrière est journalisé et remonté.

`POST /api/filing/dossier/export` écrit l’archive portable : `manifest.json`, `data.json` (les tables, montants en chaînes de centimes) et `documents/<nom généré>` pour chaque justificatif enregistré. Un fichier du disque qui n’est pas en base, ou dont le nom commence par un point, n’est pas archivé. Le manifeste porte la date, la version, la révision de schéma, les millésimes fiscaux et les empreintes. Aucun secret. Le nom est `dossier-<horodatage>.zip`, distinct de `sololmnp-*.zip`.

`GET /api/filing/dossier/exports` liste ces archives avec la même forme que les sauvegardes fichier (clé `backups`) : date, taille, versions, empreinte et dernier contrôle. `POST /api/filing/dossier/exports/verify` rejoue les contrôles (chemins, doublons, tailles, empreintes, tables, compteurs, signatures des justificatifs) et enregistre le résultat dans `dossier-exports/integrity.json`, à côté des archives, pas dedans. `GET /api/filing/dossier/exports/preview?filename=` compare les nombres d’écritures et d’exercices. Rien n’est écrit.

`POST /api/filing/dossier/restore` exige `confirmation: "RESTAURER"` et une archive de la liste. Il refuse un nom qui n’est pas `dossier-*.zip`, une empreinte fausse, un schéma différent ou un justificatif qui ne correspond plus à la ligne. Avant le remplacement, une archive de l’état actuel est créée. Les triggers utilisateur sont suspendus le temps de remplacer toutes les lignes, puis réactivés avant le commit. Les clés étrangères restent actives. Les liens d’une table vers elle-même sont vidés puis rétablis pendant cette suspension : une écriture validée n’est pas corrigée une à une. Les justificatifs du stockage sont ensuite alignés sur l’archive. Si cette copie échoue, les lignes d’avant sont remises. Si ce retour arrière échoue, le message est journalisé et l’archive préalable reste disponible. Un fichier dont le nom commence par un point (`.gitkeep`) est laissé en place ; les autres fichiers non enregistrés sont retirés.

`GET /api/filing/storage` indique le stockage (`local` ou `blob`), la taille maximale et le seuil d’envoi direct. `BLOB_READ_WRITE_TOKEN` vide : disque local (`DOCUMENTS_DIR`, archives dans le dossier voisin `dossier-exports`). Jeton présent : Vercel Blob privé. Le jeton ne sort pas de l’API.

`GET /api/filing/documents` liste les justificatifs : nom, date, type, taille, empreinte SHA-256 et écriture liée (numéro, date, pièce). Aucune URL de stockage. `GET /api/filing/documents/{id}/content` renvoie le fichier, avec `Cache-Control: private`. `DELETE /api/filing/documents/{id}` retire la ligne puis le fichier, sans modifier l’écriture. `POST /api/filing/documents` dépose un contenu en base64 tant qu’il tient dans le corps d’une fonction. Au-delà, avec Blob, `POST /api/filing/documents/upload-grant` fournit un jeton d’envoi limité à un chemin, un type et une taille, puis `POST /api/filing/documents/complete` relit l’objet et vérifie la signature, la taille et l’empreinte avant d’enregistrer la ligne. `GET /api/filing/entries` cherche une écriture par numéro, date ou pièce, sans exposer d’identifiant interne. `POST /api/filing/documents/{id}/link` enregistre cette liaison sur le justificatif seulement.

Conserver plusieurs générations hors machine et chiffrer les archives qui contiennent des données personnelles.
